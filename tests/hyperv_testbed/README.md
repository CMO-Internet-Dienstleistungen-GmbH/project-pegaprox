# Hyper-V migration testbed

What the Hyper-V migration work can be proved against without a Hyper-V host, and
what it deliberately cannot. Part of fork issue #15.

A Hyper-V host cannot be emulated: there is no Hyper-V in a container. What *can*
be reproduced is everything downstream of the host's answers — the disk formats,
the file transport, the conversion, and the content arriving intact. Those are
the parts where a mistake destroys data, so those are the parts that get a real
prüfstand rather than a mock.

## What is real here

| Piece | How | Real? |
|---|---|---|
| VHDX fixed and dynamic images | `qemu-img`, the same tool the import path uses | Real format, real reader |
| Disk content survives conversion | A known byte pattern at head, middle and tail | Real, byte-compared |
| Multi-disk mapping | Two images with different content | Real: swapping them fails |
| SMB read-only file access | A Samba container serving the fixtures | Real protocol |
| The migration's own transfer commands | `verify_transfer.sh` mounts the share once and converts dynamic, fixed and a second disk with the exact strings `hyperv_transfer.py` builds | Real mount, real conversion, checksum-compared |
| What a large sparse import costs | `measure_large_import.sh` converts a 64 GiB sparse VHDX and repeats it onto a target too small | Real sizes, real memory, real ENOSPC |
| The console relay against a Guacamole daemon | `verify_console.sh` completes the handshake and carries it to a websocket client | Real guacd, real protocol |
| PowerShell script behaviour | `pwsh` with stub cmdlets standing in for the Hyper-V module | Real parser and real execution, stubbed data |
| Hyper-V answers (VM, disk, NIC, firmware metadata) | Fixtures generated by running the real scripts under stub cmdlets | Shape is real, values are synthetic |
| WinRM/PSRP transport | Not reproduced | **No** — needs a host |
| Proxmox target | `verify_target.sh` runs the product's commands on a node somebody provides | Real `pvesm alloc`, real block device, checksum off the volume |
| Cleaning up a failed import | `verify_cleanup.py` creates a target VM the way the runner does and asks the product to remove it | Real Proxmox API: deleted, and refused when the mark is gone |

## What cannot be proved here

- **The host answers at all.** Transport, authentication and rights need a real
  WinRM endpoint. The probe in `misc/hyperv_connectivity_check.py` exists to
  measure exactly that when a host is released, and the open blocker is recorded
  in `docs/hyperv-verification.md`.
- **Differencing chains.** `qemu-img` cannot create a differencing VHDX, so an
  AVHDX chain cannot be built here. This costs less than it looks: importing a
  remaining chain is out of scope for the epic, so the requirement is that
  preflight *blocks* on one, and blocking is decided from the `ParentPath`
  metadata rather than from the file.
- **That a migrated guest boots.** Only a real target shows that.
- **That a customer's target node can mount their source share.**
  `verify_transfer.sh` proves the commands work against a Samba export on
  loopback, and `verify_target.sh` proves them on a real Proxmox node against a
  share on that node. Whether a particular node has `cifs-utils`, a route to the
  Hyper-V host and an account that may read the share stays a property of their
  environment, and the migration reports it as one rather than assuming it.

## Usage

```bash
./tests/hyperv_testbed/make_fixtures.sh          # build the disk images
./tests/hyperv_testbed/make_fixtures.sh --clean  # remove them
./tests/hyperv_testbed/verify_transfer.sh        # prove the data path end to end
./tests/hyperv_testbed/measure_large_import.sh   # measure what a large import costs
./tests/hyperv_testbed/verify_console.sh         # prove the console relay
./tests/hyperv_testbed/verify_target.sh --help   # the target half, on a real Proxmox node
python3 tests/hyperv_testbed/verify_cleanup.py   # the cleanup, on a real Proxmox node
```

`verify_target.sh` and `verify_cleanup.py` are the two scripts here that need something
this repository cannot provide: a Proxmox node. Both take every address, name and id from
the environment and refuse to guess one, so nothing about a particular installation is
written down, and `verify_cleanup.py` reads its API token from the environment so it never
reaches an argument list. `verify_cleanup.py` creates two VMs at the VMIDs it is given and
removes both again; run it with numbers nothing else uses.

What these measured is written down in `docs/hyperv-transfer.md` and
`docs/hyperv-console.md`; the matrix they feed is `docs/hyperv-compatibility.md`, which
carries the cleanup results directly.

`verify_transfer.sh` is the one that answers "does the transfer work", as opposed
to "is the transfer built the way we think". It asks
`pegaprox/core/hyperv_transfer.py` for the command strings, runs those, and
compares the converted image against the checksum the fixtures were built with.
Retyping the commands in the script would only have proved that the script
works. It needs Docker and `--privileged`, because mounting a filesystem inside
a container does.

The images are build output and are not committed. Tests that need them skip
when they are absent, so the suite stays runnable on a machine without Docker.

## Why the fixtures are generated, not written by hand

A hand-written fixture encodes what its author believed the tool returns, and an
implementation tested against it only proves the two agree. The PowerShell
fixtures here are produced by executing the implementation's own scripts under
`pwsh` with stub cmdlets, so their shape comes from PowerShell's serialiser
rather than from a guess. The disk images are produced by `qemu-img`, which is
what the import path reads them with.

That leaves the values synthetic and the structure real, which is the honest
split: a test can then fail because the code is wrong, not because the fixture
was.
